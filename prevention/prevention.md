# Failure Prevention Plan: Healthcare.gov

| # | SDLC Stage | Control Type | Concrete Engineering / Process Control | Failure Addressed |
| :--- | :--- | :--- | :--- | :--- |
| **1** | Requirements | Preventive | **Formal Requirements & Change Control:** Every requirement needed to be strictly documented, reviewed, and directly linked to testing phases. Any late modifications should have required a formal impact analysis to prevent uncontrolled scope changes and confusion. | Prevents requirements failure (C1) and uncontrolled changes (C6). |
| **2** | Testing | Preventive & Detective | **End-to-End Integration Testing:** The entire user journey—from registration and eligibility verification to final enrollment—should have been tested as one seamless flow. | Detects integration failures and broken connections between the various independent systems before launch (C3/C5). |
| **3** | Testing | Detective | **Performance & Capacity Testing:** The system should have been subjected to realistic, peak user loads before going live. Engineers needed to enforce strict, predefined limits for server capacity, database response times, and error rates. | Identifies massive scalability and capacity problems before deployment (C2/C5). |
| **4** | Release / Management | Preventive & Detective | **Independent Release-Readiness Review:** An independent, external team should have evaluated test results, unresolved bugs, and overall performance right before launch. If the system failed to meet critical criteria, the launch should have been delayed. | Prevents releasing a defective system due to schedule pressure (C7/C9). |
| **5** | Deployment | Preventive & Detective | **Staged Deployment & Rollback:** Rather than a massive national launch, the portal should have been released gradually. This approach needed to include continuous monitoring and a tested rollback plan to safely undo changes if the system crashed. | Limits the impact of operational failures and detects live problems early (C7). |
