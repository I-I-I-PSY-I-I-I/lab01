# Root-Cause Analysis: Healthcare.gov Launch

## Failure-Cause Mapping (C1 - C10)

* **C1: Requirements Failure:** Requirements were unclear, incomplete, and unstable from the start, with critical unknowns regarding expected user volume and state participation. Features were altered or delayed near the deadline, and the massive number of contractors struggled to maintain a shared understanding of the system's requirements, leading to severe integration issues.
* **C2: Assumption Failure:** CMS drastically underestimated the initial user demand, which surged to roughly five times the expected volume. Because these assumptions were never properly validated through rigorous capacity planning or testing, the system was easily overwhelmed, particularly when users tried to create accounts.
* **C3: Design / Architecture Failure:** The system's complex, interconnected architecture lacked a single technical integrator to ensure all components worked together safely. Cloud infrastructure and capacity were poorly planned and untested under realistic conditions, causing critical bottlenecks like the Enterprise Identity Management system to fail.
* **C4: Implementation Failure:** The software deployed on launch day contained known coding errors and lacked planned functionalities. Investigators found that developers were aware of these defects prior to launch but failed to adequately fix them, while poor traceability made it impossible to verify if the code actually met the project's requirements.
* **C5: Testing / Verification Failure:** The portal went live without completing necessary end-to-end and integration testing across its interconnected systems. Furthermore, testing documentation was missing fundamental pass/fail criteria, meaning CMS had no concrete evidence that the platform could handle real-world enrollment.
* **C6: Configuration / Change-Management Failure:** In the months immediately preceding the launch, CMS continuously altered the project's scope, hardware capacity, and software code. This rapid rate of change, combined with insufficient testing, made it impossible to guarantee that the final production environment was stable.
* **C7: Deployment / Operational Failure:** The platform was pushed into a live public environment despite a severe lack of readiness evidence. It was deployed with incomplete testing, known software bugs, and unverified system capacity.
* **C8: Human Factors:** The system provided poor usability, featuring confusing error messages, slow load times, and a lack of clear feedback. Consequently, confused users repeatedly refreshed pages or submitted duplicate account requests, which placed even more strain on the already failing architecture.
* **C9: Organizational / Management Failure:** The project suffered from poor leadership, inadequate contractor coordination, and a rigid adherence to the October 1 deadline. Despite receiving explicit warnings about technical and schedule risks, management pushed forward rather than allowing time to fix defects, ultimately requiring external contractors like QSSI and Accenture to rescue the project.
* **C10: Ethics / Professional Responsibility:** Multiple officials and contractors were fully aware of the severe technical shortcomings, capacity risks, and incomplete testing before launch. Releasing a highly complex system with known flaws—without properly escalating risks or reconsidering the launch date—raises major ethical concerns regarding risk communication and the duty to protect the public from foreseeable failures.
